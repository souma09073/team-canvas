# コード解説(新版 `processing/manjaro_v2/`)

このゲームを**自分で書き換えるための地図**。
「◯◯を変えたい」から逆引きできるように書いてある。

対象は `processing/manjaro_v2/`。旧版 `processing/manjaro/` は退避用なので触らない。

---

## 0. まず知っておくこと

### ファイルの役割

| ファイル | 何が書いてあるか | 行数 |
|---|---|---|
| `manjaro_v2.pde` | 起動と入力。毎フレームの入口 | 138 |
| **`Config.pde`** | **調整する数値。全部ここ** | 233 |
| **`Regions.pde`** | **4ステージの定義(速度・長さ・難易度・港名)** | 223 |
| `Course.pde` | コース生成(食べ物・岩・女性の配置) | 320 |
| `Game.pde` | ゲームのルール。**描画のコードが1行も無い** | 482 |
| `View3D.pde` | 3D描画(地面・食べ物・港・主人公) | 466 |
| `Hud.pde` | 走行中の画面表示(ゲージ・タイム) | 360 |
| `Screens.pde` | タイトル / フェリー / カウントダウン / ゴール | 275 |
| `ShotPanel.pde` | 右下のマンジャロのパネル | 102 |
| `Colors.pde` | 色の名前 | 94 |
| `Fonts.pde` | 日本語フォントの読み込み | 49 |
| `Assets.pde` | 画像の読み込み | 39 |

**迷ったら `Config.pde` を開く。** 数値の8割はそこにある。

### 座標の決まり

```
X … 横。+ が画面の右
Y … 高さ。+ が上
Z … 前後。+ が進行方向(スタートからの距離)
```

`z` が **「スタートから何 units 進んだか」**。この1つの数字がゲーム全体を動かしている。
食べ物も岩も港も「z が何番か」で置かれていて、主人公の `z` がそこに届いたら当たる。

レーンは `0=左 1=中 2=右` の3本。`laneToX(lane)` で横位置に変換する。

### 全体の流れ(毎フレーム)

```
manjaro_v2.pde の draw()
  ├ dt を計算(実測。1/frameRate は使わない)
  ├ game.update(dt)   … ルールを進める(Game.pde)
  ├ view.drawWorld()  … 3Dの世界を描く(View3D.pde)
  └ hud.draw()        … 上に画面表示を重ねる(Hud.pde)
```

**ルールと描画が完全に分かれている。** ゲームの仕組みを知りたいなら `Game.pde` だけ読めばいい。見た目を変えたいなら `View3D.pde` と `Hud.pde` しか触らなくていい。

## 1. ステージを生成する

### どこにあるか

`Regions.pde` の `buildRegions()`。**ステージの定義はこの表が全て。**

```java
regions = new Region[] {

  region("沖縄")
    .ports("沖縄 糸満", "那覇港")          // 出発地, ゴールの港
    .speed(95, 1.5, 25)                    // 開始速度, 加速倍率, 目標秒数
    .look(C_OKINAWA_LAND, C_OKINAWA_SEA, "food_okinawa.png", "sky_okinawa.png")
    .food(0.50, 0.80, 16, 8),              // 食べ物の間隔(秒), 血糖の上昇, 減少

  region("本州 西日本")
    .ports("鹿児島港", "大阪港")
    .speed(115, 1.5, 25)
    .look(C_WEST_LAND, C_WEST_SEA, "food_west.png", "sky_west.png")
    .food(0.42, 0.66, 20, 10)
    .rest(),                               // ← 中間地点。ここだけ止まる

  region("本州 東日本")
    ...
    .dense(0.45, 0.62),                    // 密集地帯(エリア内の45%〜62%)

  region("北海道")
    ...
    .dense(0.38, 0.66)
};
```

### 設定できること

| 書き方 | 意味 |
|---|---|
| `.ports("出発地", "ゴールの港")` | フェリー画面と「まもなく◯◯港」に出る名前 |
| `.speed(開始速度, 加速倍率, 目標秒数)` | 速度と、そこから決まる長さ |
| `.look(陸の色, 海の色, 食べ物の画像, 背景の画像)` | 見た目 |
| `.food(間隔min秒, 間隔max秒, 上昇, 減少)` | 難易度 |
| `.dense(開始割合, 終了割合)` | 密集地帯。書かなければ密集なし |
| `.rest()` | 走り終えたあと**止まって**途中経過を見せる |

### やりたいこと別

**ステージを5つに増やす**
→ 配列に `region("九州")...` を1行足すだけ。
マンジャロの使用回数(1エリア1回)もゴール画面の文言も**エリアの数から自動で決まる**ので、他は何も直さなくていい。

**ステージの順番を変える**
→ 配列の並び順を入れ替えるだけ。位置(`startZ`/`endZ`)は自動で計算される。

**ステージを短くする**
→ `.speed(...)` の第3引数(目標秒数)を下げる。25 → 20 で1ステージ20秒。
**長さは自分で計算しなくていい。** 「目標秒数 ÷ 速度」から自動で求まる。

**全体をもっと速く / 遅くする**
→ `Config.pde` の `SPEED_SCALE`(現在 1.3)。**これ1つ。**
上げるとコースも自動で伸びるので、1ステージの秒数は 25 秒のまま変わらない。
レーン移動の速さも一緒に上がるので「見えているのに届かない」にならない。

**止まる場所を変える(中間地点をどこにするか)**
→ `.rest()` を付け替える。今は本州西の後(2ステージ目の後)。

### ステージとステージの間の仕組み

**エリア同士は 900 units の海で引き離してある**(`Config.pde` の `REGION_GAP`)。

```
沖縄 [0 ... 3807] ~~~ 海900 ~~~ 本州西 [4707 ... 9316] ~~~ 海900 ~~~ ...
```

なぜ空けているか: 描画距離が 420 units なので、**900 空けておけば港に立っても次のエリアが見えない。** 空けないと、船に乗る前から次の土地の道が見えてしまい「同じ道の続きを走っているだけ」に見える。

**海の上は走らない。** 船に乗ると `Game.pde` の `leaveFerry()` が `z` を次のエリアの先頭へ飛ばす。

```java
void leaveFerry() {
  z = regions[regionIndex].startZ;   // 船に運ばれた
  lane = 1;  x = laneToX(1);
  startCountdown();
}
```

### 注意点

- **`.dense()` の引数名を `from` / `to` にしてはいけない。** Processing のパーサーが `to` を予約語として扱い、`Syntax Error - Error on parameter or method declaration` で止まる。実際に2回ハマった。
- 密集地帯の割合は**エリア内**の割合。コース全体ではない。だからエリアの長さを変えても密集の位置がずれない。

## 2. 食べ物を生成する

### どこにあるか

- **どれくらい詰めるか** → `Regions.pde` の `.food(...)`
- **どう並べるか** → `Course.pde`

この2つは役割が分かれている。**数値をいじりたいだけなら `Course.pde` は開かなくていい。**

### 数値(`Regions.pde`)

```java
.food(0.50, 0.80, 16, 8)
//    ↑     ↑     ↑   ↑
//    │     │     │   └ 血糖の毎秒減少
//    │     │     └── 食べ物1つの血糖上昇
//    └─────┴──────── 食べ物の間隔(秒)。0.50〜0.80秒に1個
```

現在の表:

| ステージ | 間隔 | 上昇/減少 | 密集地帯 |
|---|---|---|---|
| 沖縄 | 0.50〜0.80秒 | +16 / -8 | なし |
| 本州西 | 0.42〜0.66秒 | +20 / -10 | なし |
| 本州東 | 0.38〜0.58秒 | +24 / -12 | あり |
| 北海道 | 0.32〜0.50秒 | +28 / -14 | あり(長い) |

**なぜ「秒」で持っているか(重要)**

距離(units)で指定すると、**速いステージほど食べ物が高速で流れてきて、難しさが速度に勝手に引きずられる。** 秒で持てば「何秒に1個来るか」を設計どおりに保てる。生成時にその地点の速度を掛けて距離に直している:

```java
float gapSec = r.foodGapSecMin + rng.next() * (r.foodGapSecMax - r.foodGapSecMin);
z += gapSec * r.speedAt(z);
```

**必要ペースの考え方**

```
必要ペース = 上昇 ÷ 減少 秒に1個
```

今はどのステージも **2.0秒に1個**(16÷8 = 20÷10 = 24÷12 = 28÷14)。
つまり**忙しさは全ステージ同じで、1回のミスの重さだけが増していく。**

上昇と減少を**同じ倍率で**変えれば、忙しさを変えずに「メーターの跳ね方」だけ調整できる。片方だけ変えるとゲームの根本が変わるので注意。

### 配置のルール(`Course.pde`)

**まばら区間**(ステージの大半)
一定間隔で1個ずつ置く。**直前と同じレーンには置かない**(`pickLaneAvoiding()`)。同じレーンに置き続けると、走る側は動かずに拾えてしまい「レーンを選ぶ」という判断そのものが消える。

**密集地帯**(`.dense()` を書いたステージだけ)
一定間隔で「列」を作り、**各列は1レーンだけ空ける。** 空きレーンは左右に振れる(`weaveOpenLane()`)。ここは「拾いに行く」場所ではなく「よけ続ける」場所。

**絶対の原則: 1列に置く食べ物は最大2個。必ず1レーンは逃げ道を残す。**
3個並べて回避不能にすると、プレイヤーは理不尽に感じる。

### やりたいこと別

**食べ物を減らす / 増やす**
→ `.food()` の間隔(最初の2つ)を大きく / 小さくする。

**メーターの動きを穏やかにする**
→ `.food()` の上昇と減少を**同じ倍率**で下げる。例: `16, 8` → `12, 6`。

**密集地帯を足す**
→ そのステージに `.dense(0.4, 0.6)` を書く。

**密集地帯の詰まり具合を変える**
→ `Config.pde` の `DENSE_ROW_SEC`(現在 0.34秒に1列)。

**毎回同じコースなのを変えたい**
→ `Config.pde` の `COURSE_SEED`。同じ数字なら毎回同じ配置になる(タイムを競うために固定してある)。

### 注意点

**乱数を引く回数を変えてはいけない。** `Course.pde` の `Rng` は種を固定した乱数。1回でも引く回数がずれると、それ以降の抽選が全部ずれて**コース全体が別物になる。** 特に `weaveOpenLane()` は1列につき必ず1回だけ呼ぶこと(コードにも警告コメントがある)。

## 3. ゴールを生成する

### 考え方

**各ステージのゴールは「港」。** ゴールゲートをくぐった先に桟橋があり、船が停泊している。

なぜこうしたか: 以前はステージの境目に何も無く、**「一度止まって、また同じところから走らされている」ように見えていた。** ゲート → 桟橋 → 船、と目に見える順番で並べることで「ここまで走りきった」「この船で次の土地へ渡る」の2つが絵として伝わる。

### どこにあるか

`View3D.pde` の `drawPort()` とその下の3つ。

```java
void drawPort(Game g) {
  Region r = regions[g.regionIndex];
  float d = r.endZ - g.z;
  if (d > DRAW_DIST || d < -PORT_DEPTH * 2) return;   // 遠すぎる / 通り過ぎた
  float a = fadeAlpha(max(0, d));

  drawGoalGate(r.endZ, a);                     // ゴールゲート
  drawPier(r.endZ, a);                         // 桟橋
  drawShip(r.endZ + PORT_DEPTH * 0.7, a);      // 停泊している船
}
```

- `drawGoalGate(z, a)` … 黄色い門。柱2本 + 横棒
- `drawPier(z, a)` … 桟橋の板 + 杭8本
- `drawShip(z, a)` … 船体・甲板の建屋・操舵室・煙突(全部 `box()`)
- `drawStartLine(g)` … ステージの始まりの白黒の市松

### やりたいこと別

**船を大きく / 小さくする**
→ `drawShip()` の `box(9.0, 3.6, 26)` などの数字。単位はワールド units(レーン幅が 4)。

**船の色を変える**
→ `Colors.pde` の `C_SHIP_HULL` / `C_SHIP_DECK` / `C_SHIP_CABIN` / `C_SHIP_FUNNEL`。

**桟橋を長くする**
→ `Config.pde` の `PORT_DEPTH`(現在 34)。

**ゴールテープや紙吹雪を足す**
→ `drawPort()` に描画を1つ足す。ここが港まわりの入口になっている。

**「まもなく◯◯港」の出るタイミング**
→ `Config.pde` の `PORT_NOTICE_SEC`(現在 4秒手前)。表示そのものは `Hud.pde` の `drawPortApproach()`。

### ゴールを判定しているのはどこか

**描画とは別。** `Game.pde` に2ヶ所ある。

```java
// ステージのゴール(港に着いた)→ 船に乗る
boolean updateRegion(float dt) {
  if (regionIndex >= regions.length - 1) return false;   // 最終ステージには港が無い
  if (z < regions[regionIndex].endZ)     return false;   // まだ着いていない
  ferryFromRegion = regionIndex;
  regionIndex++;
  state = STATE_FERRY;
  return true;
}

// ゲーム全体のゴール(最終ステージの終わり)
void checkGoal() {
  if (z >= COURSE_LENGTH) goal();
}
```

**`View3D` の港を消してもゴールはできる。** 見た目と判定が独立しているので、片方だけ壊れることがある。港の位置を動かしたいときは `Regions.pde` の長さを変えること(両方が `endZ` を見ている)。

## 4. キャラ操作

### 入力を受けるところ

`manjaro_v2.pde` の `keyPressed()`。**状態によって受け付けるキーが変わる。**

```java
void keyPressed() {
  if (game.state == STATE_READY)     { Enter でスタート }
  if (game.state == STATE_FERRY)     { 中間地点のときだけ Enter で出港 }
  if (game.state == STATE_COUNTDOWN) { 何も受けない(構える時間) }

  // 走行中
  ←/ A → game.moveLeft()
  →/ D → game.moveRight()
  スペース → game.tryShot()    マンジャロ
  Z       → game.tryZone()     ゾーン
  R       → game.reset()       リトライ
}
```

**入力は `Game` のメソッドを呼ぶだけ。** ここに処理を書かない。

### 横移動の仕組み

`Game.pde` に2つの変数がある。**この区別が大事。**

```java
int   lane = 1;   // 目標のレーン(0/1/2)。キーで即座に変わる
float x = 0;      // 実際の横位置。lane へ向かって少しずつ動く
```

```java
void moveLane(float dt) {
  float targetX = laneToX(lane);
  float dx = targetX - x;
  float step = laneChangeSpeed() * dt;
  x += (abs(dx) <= step) ? dx : (dx > 0 ? step : -step);
}
```

瞬間移動ではない。**移動の途中でも当たり判定が起きるので「間に合うかどうか」がゲームになる。**

### やりたいこと別

**レーン移動を速く / 遅くする**
→ `Config.pde` の `LANE_CHANGE_BASE`(現在 24)。

ただし実際の速さは `laneChangeSpeed()` = `LANE_CHANGE_BASE × SPEED_SCALE`。
**走行速度と必ず連動させること。** 速度だけ上げると「見えているのに届かない」状態になる。

**レーンを4本に増やす**
→ `laneToX()`(`Config.pde` の末尾)と、`moveLeft()`/`moveRight()` の上限、`Course.pde` のレーン抽選(`3` と書いてある箇所)を直す。**そこそこ手が入るので、やるなら時間があるときに。**

**当たり判定を甘く / 厳しくする**
→ `Config.pde` の `COLLECT_DIST`(前後方向、現在 2.0)。
横方向は `Game.pde` の `isTouching()` の `LANE_WIDTH * 0.45`。

```java
boolean isTouching(float objZ, int objLane) {
  return abs(objZ - z) < COLLECT_DIST
      && abs(laneToX(objLane) - x) < LANE_WIDTH * 0.45;
}
```

**主人公の見た目を変える**
→ 画像を差し替えるなら `data/images/player.png`。
大きさは `Config.pde` の `PLAYER_IMG_HEIGHT`(現在 3.4)。
画像を使わない図形版は `View3D.pde` の `drawPlayerShapes()`。
`Config.pde` の `USE_IMAGES = false` で図形版に切り替わる(**何かおかしくなったら、まずここを false にして切り分ける**)。

**走りの上下ゆれ**
→ `View3D.pde` の `drawPlayer()` の `bobRate`。周期を走行速度に比例させている。比例させないと、速いときに足が滑って見える。

### 止まっているときの扱い

血糖で倒れる / 岩に当たると**完全に止まる。**

```java
if (isStopped()) {
  elapsed += dt;                        // 経過タイムだけが進む
  stopTimer = max(0, stopTimer - dt);
  return;                               // 前進も血糖も当たり判定も全部飛ばす
}
```

減速ではなく停止にした理由: 減速だと「3秒間40%だから実質1.8秒ロス」という分かりにくい計算になる。**完全に止めれば、止まった秒数がそのまま失う時間になる。**

- `COLLAPSE_STOP_SEC = 2.0`(血糖で倒れた)
- `ROCK_STOP_SEC = 0.8`(岩。見て避けそこねただけなので短い)

## 5. 血糖値の動き

**このゲームの中心。** 他の全部がこれを軸に回っている。

```
何もしないと減り続ける      → 食べないと倒れる
食べ物を取ると大きく上がる  → 食べすぎても倒れる
```

この2つに挟まれた状態を保つのがゲームの中身。

### 数値がどこにあるか

**2ヶ所に分かれている。**

| | 場所 | 内容 |
|---|---|---|
| ステージごとに違う | `Regions.pde` の `.food(...)` | 上昇幅・毎秒減少 |
| 全ステージ共通 | `Config.pde` | 安定域・高血糖の閾値・猶予 |

```java
// Config.pde
final float DRAIN_HIGH_MULT   = 1.5;   // 高血糖のときは減少が何倍になるか
final float STABLE_MIN        = 35;    // 安定域(緑)の下限
final float STABLE_MAX        = 65;    // 安定域(緑)の上限
final float HYPER_THRESHOLD   = 65;    // これを超えると高血糖カウントダウン開始
final float HYPER_GRACE_SEC   = 3;     // 猶予(秒)
final float HYPER_RESET_BELOW = 65;    // ここまで下げれば解除
final float DANGER_ZONE       = 15;    // これ未満で低血糖の警告(青)
final float GLUCOSE_RESET     = 50;    // 治療後 / 港を出るときの値
```

### 動かしているコード(`Game.pde`)

**減る**

```java
void updateGlucoseDrain(float dt) {
  if (isCollapsed()) return;                          // 治療中は減らない
  float base = drainPerSec() * (glucose > STABLE_MAX ? DRAIN_HIGH_MULT : 1);
  float rate = base * (shotEffect > 0 ? SHOT_DRAIN_MULT : 1);
  glucose -= rate * dt;
}
```

**上がる**

```java
void checkFoodPickup() {
  if (shotEffect > 0) return;      // マンジャロ効果中は食べ物に反応しない
  for (Food f : course.foods) {
    if (f.eaten || !isTouching(f.z, f.lane)) continue;
    f.eaten = true;
    glucose += foodGain();         // ステージごとに違う
    ...
  }
}
```

**上に振り切る(高血糖)**

```java
void checkHyperglycemia(float dt) {
  glucose = min(100, glucose);            // 上限は100
  if (hyperTimer > 0) {
    if (glucose <= HYPER_RESET_BELOW) { hyperTimer = 0; return; }   // 戻せた
    hyperTimer -= dt;
    if (hyperTimer <= 0) doCollapse("高血糖");
    return;
  }
  if (glucose > HYPER_THRESHOLD) hyperTimer = HYPER_GRACE_SEC;      // 開始
}
```

**即座には倒れない。猶予の間に下げれば助かる。**
「自分で下げる行動を取れば助かる / 取らなければ倒れる」形にするための仕組み。

**下に振り切る(低血糖)**

```java
void checkHypoglycemia() {
  if (glucose <= 0) doCollapse("低血糖");
}
```

### やりたいこと別

**低血糖で倒れやすくする** → `.food()` の減少を上げる
**高血糖で倒れやすくする** → `DRAIN_HIGH_MULT` を下げる(戻すのに時間がかかる)
**全体を易しく** → `HYPER_GRACE_SEC` を上げる(猶予が伸びる)
**安定域(緑)を広げる** → `STABLE_MIN` を下げる

### 変えるときの注意(3つ)

**① `STABLE_MAX` を変えるときは3ヶ所セット**
`STABLE_MAX` / `HYPER_THRESHOLD` / `HYPER_RESET_BELOW` を同じ数字にする。バラバラだと「緑なのに高血糖警告が出る」といったことが起きる。

**② 高血糖が「確定死」になっていないか**

```
(100 - STABLE_MAX) ÷ (減少 × DRAIN_HIGH_MULT) が HYPER_GRACE_SEC を超えたら確定死
```

北海道(減少14)なら `35 ÷ 21 = 1.67秒` 対 猶予3秒 → 助かる。
沖縄(減少8)なら `35 ÷ 12 = 2.9秒` 対 猶予3秒 → **余裕0.1秒しかない。**
沖縄は上昇+16なので100に届くには3連続で食べる必要があり、まず起きない。が、上昇を上げるならここを再計算すること。

**③ 上昇と減少はセットで考える**
片方だけ変えると必要ペース(上昇÷減少)が変わり、ゲームの忙しさそのものが変わる。

### マンジャロとの関係

**マンジャロは1ステージにつき1回だけ打てる。**

現実のマンジャロは**週1回の持続性の薬**で、血糖が上がった瞬間に打つ薬ではない(それはインスリンの役割)。1ステージ = 1週間 とみなして回数を制限している。**ただし、いつ打つかは自由。**

効果は「**食べ物が無効になる**」(`SHOT_EFFECT_SEC = 5.0` 秒)。
食べ物を**消すのではなく、そこに残ったまま素通りする**(食欲が失せた状態)。血糖には直接影響しない。

```java
void checkFoodPickup() {
  if (shotEffect > 0) return;   // 消費もされない。素通りする
```

**下降は止まらない。80%に緩めるだけ**(`SHOT_DRAIN_MULT = 0.8`)。
完全に止めると「打てば安全」になり、**マンジャロの危険性が表現できなくなる。**
だから効果中は血糖が下がる一方で、**早く打ちすぎると低血糖に落ちる。** これが狙い。

**描く順番は `Hud.draw()` の中に並んでいる。** 後に書いたものが上に重なる。

### 座標の決まり(いちばん大事)

**画面は常に 1280 × 720 の座標で書く。** 実際のウィンドウの大きさは気にしなくていい。

```java
void begin() {
  hint(DISABLE_DEPTH_TEST);
  camera();                                    // 3Dのカメラを戻す
  ortho();
  noLights();
  translate(designOffsetX, designOffsetY);     // 画面比のズレぶんの余白
  scale(designScale);                          // 実ウィンドウへの倍率
}
```

だから `text("タイム", 640, 16)` と書けば、どのPCでも同じ位置に出る。
**解像度や表示倍率の違うPCでレイアウトが崩れない**のはこの仕組みのおかげ。

`end()` で `hint(ENABLE_DEPTH_TEST)` に戻している。**戻し忘れると次のフレームの3Dが壊れる。**

### 文字を出す

```java
setText(fontBig, 30);          // フォントと大きさ
textAlign(CENTER, TOP);
fill(255);
text("表示したい文字", SCREEN_W * 0.5, 16);
```

フォントは3種類(`Fonts.pde`)。`fontBig` / `fontMid` / `fontSmall`。

**日本語は必ずこの `setText()` を通すこと。** Processing の標準フォントは日本語を描けない。`Fonts.pde` が PC にあるフォント(Meiryo UI など)を探して読み込んでいる。**別のPCで日本語が豆腐(□)になったら `Fonts.pde` の候補リストにそのPCのフォント名を足す。**

### 色

`Colors.pde` に名前が付いている。`fill(221, 34, 85)` と書かれていても何の色か分からないので、`C_WOMAN` のように名前で引く。

血糖ゲージの配色には意味がある:

```
濃紺 → 青 → 黄 → 緑 → 赤
       ↑                ↑
    低血糖            高血糖
```

**低血糖側を青にしているのは、高血糖側の赤と一目で区別するため。**
同じ赤にすると、上に振り切ったのか下に振り切ったのか一瞬で判断できない。
警告の点滅リズムも変えてある(高血糖=等間隔、低血糖=鼓動のような周期)。

### やりたいこと別

**表示の位置を変える** → その関数の座標の数字。1280×720 の中で考える。
**表示を1つ足す** → `Hud.pde` に関数を書き、`draw()` の並びに1行足す。
**表示を消す** → `draw()` の並びからその行を消す(関数は残しておける)。
**色を変える** → `Colors.pde`。

**タイトル画面の文言を変える**
→ `Screens.pde` の `drawTitle()`。
**ルールの数値は CONFIG から組み立ててある**ので、数値を変えても説明文が古くならない:

```java
text("血糖値を " + int(STABLE_MIN) + "〜" + int(STABLE_MAX) + "(緑)に保て。", ...);
```

**ゴール画面の締めの一文**
→ `Screens.pde` の `closingLine()`。**ここがこのゲームの主題。**
マンジャロを何回使ったかで返ってくる言葉が変わる。割合で判定しているので、ステージ数を変えてもそのまま動く。

### 3Dの上に2Dを重ねる注意

`View3D.pde` の `screenX()` / `screenY()` は **3Dのカメラが有効な間しか正しい値を返さない。**
主人公の横の縦バーは、HUD が `camera()` でリセットする前に位置を計算して覚えている:

```java
// manjaro_v2.pde の draw()
view.computeMiniGaugePos(game);   // ← HUD より先に呼ぶ
hud.draw(game);
```

順番を入れ替えるとバーが変な位置に出る。

## 7. よくある落とし穴

| 症状 | 原因 |
|---|---|
| 実行ボタンを押しても開かない | 外部でファイルを書き換えた。**スケッチを閉じて開き直す** |
| `Syntax Error - Error on parameter or method declaration` | 変数名に `to` を使った。Processing の予約語 |
| 日本語が □ になる | `Fonts.pde` の候補にそのPCのフォントが無い |
| コースが別物になった | 乱数を引く回数が変わった(`Course.pde` の警告コメント参照) |
| 画面が真っ暗 / 3Dが壊れる | `hint(ENABLE_DEPTH_TEST)` を戻し忘れ |
| 絵の色が濁って暗い | ビルボードに `noLights()` を掛け忘れ |
| 別PCで画面が収まらない | `Config.pde` の `FULLSCREEN = true` にする |
| 何かおかしい(切り分け) | `USE_IMAGES = false` で図形表示に戻して確認 |
